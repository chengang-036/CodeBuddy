# 0019-TB1990-2 双人联机合作版 · 设计方案

> 目标：两名玩家各自用手机，**同时在线打同一盘**坦克大战，两人目标一致——一起扛住敌人，守住老巢。
>
> 硬约束：**完全不改动现有 `tank1990/` 工程**。本目录是独立新工程，旧工程一行不动。

---

## 一、玩法定义（先把规则钉死，再谈技术）

| 项 | 规则 |
|---|---|
| 模式 | **合作守家**（经典 1990 的 2P 模式），不是互相对打 |
| 每人 | 1 辆坦克，颜色区分（P1 黄 / P2 绿），各自独立生命 |
| 共同目标 | 老巢（老鹰）不被击毁；关卡敌人清完即过关 |
| 共享 | 关卡地形、敌人队列、道具、老巢血量、过关进度 |
| 生命 | 两人各自 3 条命；一人打光后可旁观，等队友过关救回（或直接判负） |
| 敌人 | 单人为 20 辆；双人建议 28 辆，同屏上限 4→6，避免两人抢不到怪 |
| 失败 | 老巢被毁 → 立即失败；两人生命同时耗尽 → 失败 |
| 友军伤害 | **关闭**（合作模式下误伤只会吵架，不建议开） |

**为什么先定规则**：合作模式里"敌人 AI 跑在哪一端"直接决定架构。合作模式下敌人是确定性的，两端各跑一份即可——这正好让帧同步方案成立。

## 二、技术路线选型

| 方案 | 同步内容 | 带宽 | 延迟敏感度 | 服务器成本 | 改造量 | 结论 |
|---|---|---|---|---|---|---|
| A. 状态同步（服务器权威） | 服务器跑逻辑，20Hz 广播快照 | 每帧 1–3KB，约 20–60KB/s | 低（客户端插值掩盖） | **高**：每局占 CPU，房间数受限于核数 | 大：要把整套战斗逻辑搬到服务端 | 过重 |
| B. **帧同步（lockstep）** | 只同步**输入**（方向+开火位掩码） | 每帧 < 20 字节，约 1KB/s | 中（等最慢玩家） | **极低**：只做房间+排序+广播 | 中：要做确定性改造 | **选它** |
| C. 云开发实时推送 / 数据库 watch | 数据变更推送 | 低 | 高（100–300ms，秒级抖动） | 中 | 小 | 不适合实时操作 |

### 为什么坦克大战特别适合帧同步

1. **状态量极小**：同屏 6 辆坦克 + 十几颗子弹 + 13×13 地形，状态哈希不到 1KB。
2. **动作离散**：坦克只有 4 个方向，没有"摇杆角度"这类连续量，输入天然可以压成 1 字节。
3. **速度慢**：坦克每帧移动几个像素，人对 50–100ms 的输入延迟不敏感（对比格斗游戏完全不能接受）。
4. **判定确定性**：碰撞是格子对齐的 AABB，不涉及物理引擎的浮点积分。

顺带三个白送的好处：
- **输入历史就是录像**——回放、观战、举报复现全都免费。
- **服务器极轻**：不跑逻辑，一台 1 核 2G 能挂几百个房间。
- **断线重连简单**：补发缺失的输入帧即可，不用传整个场面。

## 三、整体架构

```
        ┌─────────────┐        ┌──────────────┐        ┌─────────────┐
        │  手机 A     │        │  中继服务器  │        │  手机 B     │
        │  房主       │        │  (不跑逻辑)  │        │  加入者     │
        └──────┬──────┘        └──────┬───────┘        └──────┬──────┘
               │  wss                  │  wss                  │
   创建房间 ───┼──────────────────────▶│◀──────────────────────┤ 加入房间(4位码)
               │◀── seed + 起始帧号 ───┤─── seed + 起始帧号 ──▶│
               │                       │                       │
   每帧上行    │ {frame, mask}         │         {frame, mask} │
   本地输入 ───┼──────────────────────▶│◀──────────────────────┤
               │                       │                       │
               │◀─ {frame, [maskA,    │    ─ 按帧号排序后广播  │
               │      maskB]} ─────────┤──────────────────────▶│
               │                       │                       │
   收到该帧全部输入 → 本地 step() → 渲染 │       同样 step()      │
               │                       │                       │
   每 60 帧上报状态哈希 ──────────────▶│◀────────── 状态哈希 ──┤
               │        不一致 → 房主发全量快照重同步          │
```

**关键点：服务器不跑游戏逻辑。** 它只做四件事：房间管理、消息按帧号排序、广播、比对哈希。这让成本和服务端复杂度都降到最低。

## 四、帧同步内核设计

### 4.1 基本节奏

- **逻辑帧固定 60Hz**（16.667ms/帧），与渲染帧率解耦。
- 渲染层拿到两个已确认帧的状态，按真实时间做**插值**（避免 60Hz 逻辑在 120Hz 屏幕上抖）。
- 所有逻辑更新只发生在 `step(frame, inputs)` 里，**函数必须是纯的**：同样的 `(状态, 输入)` 必得同样的新状态。

### 4.2 输入提前量（这是手感的关键）

```
本地按下方向键的时刻  ──▶  打包成第 N+3 帧的输入
（不是"当前帧立刻生效"）

原因：如果立刻生效，那么"我的输入第 N 帧生效、对方的输入第 N 帧在路上"，
      本地已经用旧值算完了，两边必然分叉。
```

- **固定 3 帧缓冲（50ms）**：所有玩家的输入都统一延后 3 帧执行。
- 代价：操作到画面反馈固定多 50ms。
- 收益：只要网络抖动小于 50ms，就**完全不会卡帧**。

### 4.3 帧推进条件与超时

```
收到帧 N 的「全部玩家输入」 → 才允许推进第 N 帧
超时 200ms 仍缺输入 → 暂停并显示「等待对方…」（不是卡死）
```

不做"谁慢等谁"的无限等待，而是明确告诉玩家在等谁——体验上比黑屏卡住好得多。

### 4.4 自适应缓冲

| 实测 RTT | 缓冲帧数 | 说明 |
|---|---|---|
| < 60ms | 2 帧（33ms） | 同城/同网 |
| 60–120ms | 3 帧（50ms） | 4G/5G 常态 |
| > 120ms | 4–5 帧（67–83ms） | 跨省，手感明显变钝 |

开局握手阶段用 10 个 ping 采样 RTT，取中位数决定缓冲帧数，之后每 5 秒重新评估一次。

> **诚实说明**：跨省（RTT 150ms+）时帧同步的体验一定不如单机，这是光速决定的，任何实现都绕不过去。真要跨省流畅，只有上服务器权威 + 客户端预测，那是另一个量级的工程。

## 五、确定性改造清单（最难、最容易翻车的地方）

帧同步的全部前提是：两台手机跑同一段代码、同样的输入，**结果必须一比特不差**。现有单机版有三处会破坏这个前提。

### 5.1 固定步长（现有代码是变步长）

现有 `main.js`：

```js
var dt = last ? Math.min(0.05, now - last) : 0.016;   // ← 真实帧间隔，每帧都不同
game.update(dt);
```

手机上帧率会从 60 掉到 40 再回到 60，`dt` 每帧都不一样，两台手机的 `dt` 序列更不可能相同 → 必分叉。

**改法**：

```js
var acc = 0, STEP = 1 / 60;
function loop(now) {
  acc += Math.min(0.2, (now - last) / 1000);   // 单帧最多补 0.2s，防止卡顿后追帧爆炸
  while (acc >= STEP) { step(++frame); acc -= STEP; }
  render(acc / STEP);                          // 传插值系数
}
```

### 5.2 种子化随机（现有代码有 12 处 `Math.random()`）

现有代码里随机直接影响玩法：

| 位置 | 用途 |
|---|---|
| `game.js:313/317` | 敌人 AI 转向间隔、开火冷却 |
| `game.js:299/323` | 敌人类型抽取、AI 决策 |
| `game.js:519/520/524` | 道具掉落位置与类型 |
| `game.js:88` | 红闪敌人（带道具）的分配 |
| `level.js:242` | 关卡地形洗牌 |
| `entities.js:111` | 开火冷却抖动 |

**只要漏掉任意一处，约 10–30 秒后两端就会漂移（desync）。**

**改法**：统一换成 mulberry32 种子 PRNG，seed 由房主生成后随开局下发。`Math.random` 在逻辑层**一处都不许留**（可以用 lint 规则卡住）。

### 5.3 输入快照（现有是"当前按键状态"）

现有 `Input` 是持续状态（按住就是 true）。帧同步需要的是**"第 N 帧玩家按了什么"**的快照：

```js
var mask = 0;
if (held.UP)    mask |= 1 << 0;
if (held.DOWN)  mask |= 1 << 1;
if (held.LEFT)  mask |= 1 << 2;
if (held.RIGHT) mask |= 1 << 3;
if (held.FIRE)  mask |= 1 << 4;
// 一帧 1 字节，上行 3 帧冗余发送，丢包无感
```

### 5.4 其它确定性陷阱

| 陷阱 | 处理 |
|---|---|
| `Date.now()` / `performance.now()` 进逻辑 | 禁止，只能用于渲染与计时显示 |
| 浮点 `Math.sin/cos/pow` 跨引擎差异 | 逻辑里不用；坦克移动只用 `+=` 与比较 |
| 坐标浮点累积误差 | 建议改成**定点整数**（1 像素 = 16 单位），彻底消除 |
| `Array.sort` 不稳定排序 | 排序必须带唯一 id 作为第二比较键 |
| `for...in` 遍历顺序 | 不用；数组索引遍历 |
| 对象增删顺序影响状态哈希 | 哈希按固定字段顺序取，不遍历对象 |

## 六、网络协议（二进制，最小化）

### 6.1 上行：输入包（每帧 9 字节）

```
[0]     type = 0x01 (INPUT)
[1..4]  frame  uint32 LE
[5]     mask   uint8     位 0=上 1=下 2=左 3=右 4=开火
[6..7]  ackFrame uint16   已确认到第几帧（用于服务器裁剪历史）
[8]     seq    uint8     本端序号，防重放
```

### 6.2 下行：帧广播（每帧 3 字节 + N 个 mask）

```
[0]     type = 0x02 (FRAME)
[1..4]  frame uint32
[5]     n     uint8      本帧参与人数
[6..]   masks uint8 × n
```

### 6.3 控制消息（JSON 就够，量小）

| 消息 | 方向 | 内容 |
|---|---|---|
| `create` / `join` | C→S | 房间码（4 位数字/字母） |
| `start` | S→C | `{seed, startFrame, players:[id,slot]}` |
| `hash` | C→S | `{frame, hash}` 每 60 帧一次 |
| `desync` | S→C | 哈希不一致告警 |
| `snapshot` | 房主→对方 | 全量状态（重同步用） |
| `leave` / `ping` | 双向 | 心跳 5 秒 |

### 6.4 一致性校验

每 60 帧（1 秒）对全部可变状态算一次 FNV-1a 哈希：

```
覆盖字段：每辆坦克(id,x,y,dir,hp,level,cd) | 每颗子弹(owner,x,y,dir) | 地形位图 | 敌人队列指针 | 分数 | 老巢状态
字段顺序固定，整数入哈希
```

两端哈希不一致 → 服务器标记 desync → 房主发全量快照 → 对方强制覆盖 → 继续（期间冻结 0.5 秒）。

> 实战经验：desync 的排查极其痛苦。所以**开发期必须常开哈希对比**，别等上线才加。

## 七、服务器设计（刻意做到最简）

```
房间结构：
{
  code: "8F3K",
  seed: 123456789,
  startFrame: 1000,
  players: [{ id, slot, lastFrame, hash }],
  inputs: Map<frame, Map<slot, mask>>,   // 只保留最近 600 帧（10 秒）
  createdAt
}
```

- 单进程 Node + `ws`，**无数据库**（房间是临时的，进程重启无所谓）。
- 内存占用：一个房间约 20–50KB，1000 个房间约 50MB —— 一台 1 核 2G 绰绰有余。
- 心跳 5 秒，15 秒无响应踢出并通知对方"队友掉线"。
- **不做反作弊**：帧同步下客户端可以伪造输入，但合作模式打 PVE，作弊动机低。真要做，就在服务器复算哈希。

## 八、平台落地与硬门槛

### 网页版（先做这个）

- 需要 `wss://` 长连接。**WorkBuddy 托管是单端口反向代理，WebSocket 的 Upgrade 是否透传需要实测**——这一点我不打包票，上真机验证前不要当成已知条件。
- 若托管不支持，退路：
  1. 一台便宜云服务器（1 核 2G，几十元/月）跑 Node `ws`；
  2. 或云厂商的 WebSocket 托管服务。

### 微信小游戏

- `wx.connectSocket` 要求 **wss + 已备案域名**，并在小游戏后台配置 socket 合法域名。**这是绕不过去的硬门槛**，没有备案域名就上不了微信端。
- 微信云开发（云函数/数据库 watch）**不具备 60Hz 长连接广播能力**，不能用来做帧同步。
- 所以微信端顺序必须是：先有域名备案 → 再谈联机。

### 几档降级方案（都可以先做，不需要服务器）

| 方案 | 实现成本 | 适用 |
|---|---|---|
| **同屏双人**（一台手机左右各一组键 / 一台电脑 WASD+方向键） | 极低 | 先验证"双人合作好不好玩"，强烈建议作为第一步 |
| 同 Wi-Fi 局域网（WebRTC DataChannel，信令走极轻 HTTP） | 中 | 家里两人各拿一台设备，零服务器成本 |
| 房间码公网联机（本方案主线） | 中高 | 异地两人 |

**我的建议顺序：同屏双人 → 房间码联机。** 先用最低成本确认"合作守家"这个玩法本身站得住，再投入网络工程。

## 十、分阶段计划

| 阶段 | 内容 | 验收标准 |
|---|---|---|
| **P0**（本次已完成内核） | 确定性内核：固定步长、种子 PRNG、输入位掩码、状态哈希、帧同步模拟器 | 同一输入序列跑两遍，**状态哈希逐帧一致** |

## 十一、风险清单

| 风险 | 影响 | 应对 |
|---|---|---|
| **desync**（两端状态漂移） | 致命，且极难定位 | 开发期全程开哈希对比；逻辑层禁 `Math.random`/`Date.now`（加 lint）；用 P0 模拟器每日回归 |

| 跨省高延迟 | 手感差 | 明确告知限制；只承诺同城/同网体验 |
| 双人合作但敌人不够打 | 玩法失衡 | 双人 28 敌、同屏上限 6，按 2P 单独调表 |
