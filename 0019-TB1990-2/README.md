## 为什么做「帧同步」而不是「服务器跑逻辑」

坦克大战的状态太小了：13×13 格、6 辆坦克、十几颗子弹。让服务器每帧模拟一遍纯属浪费。

帧同步反过来——**服务器只转发玩家按了什么键，两台手机各自跑同一份逻辑**：

| | 状态同步 | **帧同步（本方案）** |
|---|---|---|
| 上行/下行 | 每帧 1–3KB 快照 | 每帧 1 字节输入 |
| 服务器 | 每局都要跑逻辑，吃 CPU | 只转发，1 核可挂几百房间 |
| 断线重连 | 要传整个场面 | 补发缺失的输入帧即可 |
| 录像/观战 | 要单独录 | 输入历史就是录像 |

代价是**必须保证确定性**：同输入 → 同结果，一比特都不能差。整个 P0 就是在解决这件事。

## 跑起来（Node，无需浏览器）

```bash
node tools/sim-lockstep.js              # 正常：8% 丢包，必须 0 分歧
node tools/sim-lockstep.js --loss 30    # 压测：30% 丢包
node tools/sim-lockstep.js --broken     # 反例：故意用 Math.random，看校验能不能抓出来
```

模拟器做的事：两个玩家端、各自的输入脚本、一条有 **延迟 30±18ms + 丢包 + 乱序** 的假网络，跑 900 帧（15 秒），**逐帧比对两端状态哈希**。

---

## 已验证的结论

| 丢包率 | 执行帧数 | 逐帧比对 | 等待对方 | 最长卡帧 | 哈希一致 |
|---|---|---|---|---|---|
| 0% | 898 | 898 | 0.2% | 0ms | ✅ |
| 8% | 843 | 843 | 6.3% | 33ms | ✅ |
| 30% | 749 | 748 | 16.8% | 83ms | ✅ |
| 50% | 646 | 645 | 28.3% | 117ms | ✅ |

**结论**：丢包只让推进变慢（等待对方），**不影响正确性**——两端逐帧哈希始终一致。这正是帧同步应有的表现。

**反例验证**：把随机源换回 `Math.random`（模拟"漏改一处随机"），第 **39 帧**（0.65 秒）就被检出 desync。说明哈希校验是有效的，不是永远绿灯。

## P0 踩到的两个坑（都已修）

### 1. 输入写指针跳号 → 永久死锁

追帧后 `pushLocal` 直接把写指针跳到 `frame + buffer`，导致中间几帧的输入**从未被写入**。两端永远等不到那几帧，永久停死。

**修法**：逐帧补齐，绝不跳号（补齐时用当前按键填充，等价于「卡顿期间玩家一直按着」）。

### 2. 只重发最近 3 帧 → 一帧永久丢失就死锁

早期重传策略是"每帧重发最近 3 帧"。一旦某帧的 3 次重发全丢，两端就永久停在那帧。

**修法**：改成批量补发 `[对方已执行的下一帧, 本地最新帧]`（最多 12 帧/包），并利用对方包里带的 `ack` 裁剪范围。这样任意一帧丢失都能在后续包中补上。

> 这两条是帧同步最典型的死锁来源，写在这里避免以后重犯。
